## 배경

외국인의 한국 체류를 지원하는 서비스라 해외 고객의 문의가 많았다. 문의는 WhatsApp,
Instagram, LINE으로 들어왔고, 고객이 활동하는 시간과 한국의 상담 시간이 겹치지 않는 경우가
많았다. 상담 시간 이후에 들어온 질문은 다음 날 아침부터 처리했기 때문에, 추가 확인이 필요한
문의는 답변을 마치기까지 며칠이 걸리기도 했다.

문의 내용을 분류해 보니 병원 시술 가격, 체류 자격과 심사 절차, 부동산 계약 과정, 서비스
수수료와 이용 방법처럼 답이 정해진 질문이 반복되고 있었다. 이 가운데 기존 자료로 답할 수 있는
질문을 자동화하면 첫 응답 시간을 줄이고, 상담원은 별도 판단이 필요한 문의에 집중할 수 있었다.

## 설계할 때 먼저 정한 기준

챗봇 한 개가 여러 제휴 병원과 서비스의 문의를 처리해야 했다. 병원마다 시술 가격과 안내가
다르므로, 질문과 관련 없는 테넌트의 자료가 검색 결과에 포함되면 잘못된 답변이나 정보 노출로
이어질 수 있었다.

답변의 정확도도 중요했다. 특히 가격과 절차는 계약이나 비용에 직접 영향을 주기 때문에, 근거가
부족한 경우에는 자동으로 답하지 않고 상담원에게 넘기는 편이 안전했다.

이 두 조건을 기준으로 검색 단계에서는 조회 가능한 자료의 범위를 제한하고, 생성 단계 이후에는
답변 품질을 평가하도록 처리 과정을 나눴다.

![다른 테넌트의 정보 혼입은 검색 전에, 근거가 부족한 답변은 발송 전에 제어한다.](cs-agent/design-criteria.svg)

## 처리 흐름

![CS 챗봇의 요청 확인, 검색, 가격 조회, 답변 생성 및 평가 흐름](cs-agent/pipeline.svg)

요청이 들어오면 사용자와 서비스 정보를 먼저 확인하고, 해당 범위 안에서 관련 문서를 검색한다.
가격처럼 변경될 수 있는 값은 원본 데이터에서 별도로 조회한다. 검색 결과와 조회 결과로 답변을
만든 뒤 평가 단계를 통과한 경우에만 고객에게 전송한다.

## 요청 컨텍스트 구성

검색 전에 고객과 관리자 중 누가 보낸 질문인지, 어느 채널과 서비스에서 들어온 요청인지
확인했다. 이 정보로 검색 범위와 답변 형식을 정했다. 같은 질문이라도 사용자 역할에 따라 조회할
수 있는 자료가 다르고, 채널에 따라 적절한 답변 길이와 형식도 달랐기 때문이다.

질문의 언어도 이 단계에서 판별해 답변 언어로 사용했다. 자료는 주로 한국어였지만 질문은 영어와
일본어 등 여러 언어로 들어왔기 때문에, 문서 검색에 사용할 언어와 최종 답변 언어는 분리해서
처리했다.

## 테넌트 단위 검색 분리

지식베이스 벡터와 가격 벡터에는 병원별·서비스별 스코프 ID를 저장했다. 검색할 때는 요청
컨텍스트에서 확인한 스코프 ID를 필터로 적용해, 해당 테넌트의 데이터만 후보에 포함했다.

벡터 검색은 문장의 유사도를 기준으로 결과를 찾기 때문에 별도 필터가 없으면 다른 병원의 비슷한
안내가 상위 결과에 포함될 수 있다. 검색 정확도를 조정하는 것만으로는 이 문제를 해결하기 어려워,
테넌트 필터는 유사도 계산보다 먼저 적용했다. 필터링한 후보는 리랭킹과 스코어링을 거쳐 다시
정렬했다.

![요청의 테넌트 스코프로 후보를 제한한 뒤 유사도 검색과 리랭킹을 적용한다.](cs-agent/tenant-filter.svg)

## 가격 정보는 원본 데이터에서 조회

가격이 필요한 질문에는 임베딩 검색 결과를 사용하지 않고 RDB와 Elasticsearch에서 현재 값을
조회했다. 진행 중인 이벤트가 있다면 함께 확인했다.

벡터에 저장된 가격은 임베딩을 생성한 시점의 값이므로 변경 사항을 바로 반영하지 못한다. 또한
가격은 유사한 값을 찾는 것이 아니라 특정 시점의 정확한 값을 가져와야 한다. 따라서 일반 안내는
문서 검색으로 처리하고, 가격처럼 자주 바뀌는 값은 원본 조회로 분리했다.

![일반 안내는 벡터에서 검색하고 가격과 이벤트는 원본 데이터에서 조회한다.](cs-agent/live-price.svg)

## 답변 평가와 상담원 이관

생성한 답변은 바로 전송하지 않고 별도 평가 단계를 거쳤다. 미리 정한 항목별 점수가 기준 이상인
경우에만 자동으로 발송했다. 기준에 미치지 못하면 생성한 답변을 폐기하고 고객지원센터 운영 시간
안내 등 기존 자동 응답을 보냈다.

자동 응답으로 처리하지 못한 대화는 상담원이 이어서 확인할 수 있게 했다. 답변이 불확실한 경우를
무리하게 자동화 대상에 포함하지 않고, 기존 상담 절차로 연결하는 방식이다.

![답변 평가 결과가 기준 이상이면 발송하고, 미달이면 기존 안내 후 상담원에게 이관한다.](cs-agent/quality-gate.svg)

     그 지점에 둔 근거. 평가를 같은 모델에 맡겼는지 별도 호출로 뺐는지도. -->

## LangChain을 사용한 부분

모델 호출과 처리 단계를 연결하는 데 LangChain을 사용했다. 모델을 교체할 때 호출 코드를 크게
바꾸지 않아도 됐고, 답변 품질과 실행 로그를 대시보드에서 확인할 수 있었다.

다만 이 프로젝트에서 작업 비중이 컸던 부분은 프레임워크 자체보다 테넌트별 검색 범위와 자동
발송 기준을 정하는 일이었다.

![테넌트 스코프와 발송 기준은 프로젝트 정책으로 두고 LangChain은 호출과 연결, 로그 확인에 사용했다.](cs-agent/langchain-role.svg)
