## 배경과 제약

호텔 콘텐츠 가운데 가격처럼 실시간성이 필요한 정보를 제외한 나머지는 배치로 미리 가져와
DB에 적재했다. 약 250만 개 호텔의 정보를 모두 채우려면 공급사 API를 약 800만 번 호출해야
했다.

이 API는 운영 서비스도 실시간으로 사용하고 있었다. 전체 호출량이 공급사 한도를 넘으면
429 Too Many Requests가 발생했기 때문에, 배치의 처리량을 정할 때는 API 한도 자체가 아니라
운영 트래픽이 사용하고 남은 용량을 기준으로 삼아야 했다.

![운영 요청과 배치가 하나의 공급사 API 호출 한도를 공유한다.](aimd/shared-api-budget.svg)

## 고정 동시성 검토

처음에는 동시 호출 수를 고정하는 방식을 검토했다. 운영에 영향을 주지 않으려면 트래픽이 가장
많은 시간에도 안전한 값을 사용해야 했고, 당시 기준으로 배치에 할당할 수 있는 동시 호출은
약 2건이었다. 이 값으로 800만 건을 처리하면 완료까지 한 달 가까이 걸렸다.

시간대별로 값을 따로 관리하는 방법도 있었지만, 트래픽 패턴이 바뀔 때마다 설정을 다시
조정해야 했다.

![고정 동시성은 트래픽이 적은 시간에 생기는 여유 용량을 활용하지 못한다.](aimd/fixed-concurrency.svg)

## AIMD를 적용한 동시성 조절

공급사가 지금 얼마나 여유가 있는지는 호출해 보기 전에는 알 수 없다. 그래서 값을 미리 정하는
대신 응답을 보고 조절하기로 했다. 제어 방식은 TCP 혼잡 제어에 쓰이는 AIMD(Additive
Increase / Multiplicative Decrease)를 적용했다.

정상 응답을 성공 신호로, 429와 5xx·타임아웃을 혼잡 신호로 삼았다. 연속 100회 성공하면
동시 호출 한도를 1 늘리고, 혼잡 신호가 오면 한도를 30% 줄인다.

![AIMD는 성공이 누적되면 동시 호출 한도를 늘리고 429가 발생하면 30% 줄인다.](aimd/aimd-response.svg)

시간대별 호출량을 설정으로 관리하지 않아도 되고, 공급사 한도나 운영 트래픽이 바뀌어도 배치가
응답 결과를 보고 사용할 수 있는 범위를 다시 찾아간다.

## 구현 구조

동시성 제어는 전역 리미터 하나가 담당한다. 자리를 점유하는 단위와 신호를 보내는 단위는 서로
다르지만, 둘이 바꾸는 상태는 배치 전체가 공유하는 하나다.

![자리 점유는 작업 단위, 성공·혼잡 신호는 콜 단위이며 둘이 바꾸는 한도와 점유 수는 전역 상태다.](aimd/controller-flow.svg)

감속은 이미 실행 중인 요청을 취소하지 않는다. 자리를 잡고 진행 중인 작업은 끝까지 두고, 새로
들어오는 자리 확보만 막는다.

한도의 하한은 아무리 막혀도 배치가 완전히 멈추지 않게 하기 위한 것이고, 상한은 응답 하나가
수 MB에 달해서 동시 수가 그대로 메모리 사용량이 되기 때문에 뒀다.

## 멈춘 지점부터 다시

콘텐츠 전체를 받아오는 작업은 며칠이 걸린다. 그사이 예상하지 못한 문제로 배치가 중단되면
처음부터 다시 도는 것은 며칠을 다시 쓰는 것과 같다.

그래서 어디까지 처리했는지를 남겨 두고, 다시 실행할 때 그 지점부터 이어서 처리하도록 했다.
